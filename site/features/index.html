  • Scan since 0.3.0MoreLess

    Point it at your site or docs: it finds every value you state more than one way, and where the copies disagree.

    wherefore scan

    What it does, in full Point it at a built site, a docs folder, exported notes or a live address. It reads what a person reads - pages, Markdown, text - finds every value stated in words, and reports each statement whose copies disagree, the commonest value first and every place it was said. It favours missing a disagreement over inventing one, and it needs no configuration: it is the first thing to run, before anything is declared.

  • Start a corpus since 0.1.0MoreLess

    One command starts a repository; the skill walks your agent through the first fact.

    wherefore init

    What it does, in full One command writes a wherefore.json that declares nothing yet, and the skill where Claude Code and Codex read it. From the first build on, the skill is the one the pinned release ships, and the gate says so when a copy has been edited by hand.

  • The gate since 0.1.0MoreLess

    On every push, each file must be built from the source, written by a person for a stated reason, or a capture stamped with what it shows. Anything else stops the change, and says why.

    wherefore gate

    wherefore gate

    What it does, in full On every push, each tracked file must be generated during the gate's own run, authored under a rule with a reason, or captured and stamped with what it was made from. A file nobody wrote and nobody claimed stops the change and is named; so does a generated file that differs from what is committed, and a corpus that does not settle on a second run.

  • The build since 0.1.0MoreLess

    Every asset rebuilt from the source, the same way every time, so you see exactly what a change moves.

    wherefore build

    wherefore list

    What it does, in full Every generator runs, in order, and then again: the second run must change nothing, so the corpus settles. What moved is left in place for the diff, so a change to a fact shows exactly which assets follow it, and a generated file nobody tracks is named.

  • What builds what since 0.7.0MoreLess

    A page for every repository: each file, how it is made, and what changes when a source does. One command draws it, and changes nothing.

    wherefore graph

    What it does, in full Runs every generator once, traces what each reads and writes, and draws one self-contained page: every source, script and file, with the lines between them. It changes nothing. A corpus may publish its own map, drawn in its brand's colours, with a way back to the site.

  • Proofs since 0.1.0MoreLess

    No check is trusted until it has failed: each proof plants the fault its check exists to catch.

    wherefore prove

    What it does, in full Each check ships with a proof that plants the fault the check exists to catch, runs the check, and requires it to fail naming the fault; then the tree is put back exactly. A check nobody has seen fail is not trusted, and the proofs run in CI beside the checks.

  • Retired facts since 0.1.0MoreLess

    Retire an old price, name or limit once, and nothing a person reads may say it again.

    wherefore check retired

    What it does, in full A register of what a value was, what replaced it, and why. Nothing a person reads may say the old value or phrase again, and the check names the file and the line that does - so a changed price or a renamed plan cannot linger in a help article.

  • Reach since 0.1.0MoreLess

    Wherefore changes each fact, one at a time, and checks that everything stating it changes too.

    wherefore check reach

    What it does, in full Every fact is moved, one at a time, and everything that states it must change. A fact that moves nothing is dead or copied by hand into a generator, and the probe says which; a fact a published page states reaches it by declaration. Exemptions carry a reason.

  • Claims since 0.1.0MoreLess

    Give a claim like “SOC 2 certified” a rule, and no page can say more than the rule allows.

    wherefore check claims

    What it does, in full A claim - SOC 2 certified, made in Sheffield, the fastest in its class - gets a rule saying what may be claimed, of what, and why. No page may claim more than the rule allows, and the check names the page that does.

  • Derived from elsewhere since 0.5.0MoreLess

    Copied something you can't pin, like a partner's spec sheet? The deploy fails the day its source changes.

    wherefore check upstream

    What it does, in full A copy taken from elsewhere - another company's published file, counts from another product at one of its versions - records where it was taken from and what must still match there. The check reads the source now and fails the deploy when it has moved, until the copy is taken again and the change says so.

  • A page you publish but cannot build since 0.17.0MoreLess

    A page nobody builds - your site on a hosted CMS - declared with the facts it states. Wherefore reads it live and fails when it says otherwise, quoting the page: a copy held by reading until it can be built.

    wherefore check published

    What it does, in full A page nobody here builds - the public site on a hosted CMS marketing edits - is declared with the facts it states and how each appears. The check reads it live, as a person reads it, and fails when the page says otherwise, quoting the page. It runs before a deploy and, if the client chooses, on a schedule. A copy held by reading until it can be built.

    Answers #22 asked for by @zakholdsworth · since 0.17.0

    What was planned A published section names each page nobody here builds - its address, why, and the facts it states as templates with the value in braces. wherefore check published reads the page live and fails when it says otherwise, quoting the page; a schedule is the client's choice; declaring the page counts as reach. An intermediate step: a copy until it is built from the source.

  • One palette since 0.10.0MoreLess

    Your brand lives in one file. Type a colour anywhere else and the build names the file and the line, unless the file says, with a reason, that the colour is somebody else's.

    wherefore check palette

    What it does, in full The brand's colours live in one JSON file. Every colour said anywhere else - a stylesheet, a page, a drawing, a script - fails by file and line, unless the file says, with a reason, whose colours they are. A colour quoted in code is text, not paint, and passes.

  • The pre-push hook since 0.1.0MoreLess

    A push that would ship a stale document stops before it leaves your machine.

    wherefore hook install

    wherefore hook pre-push

    What it does, in full A pre-push hook runs the gate before a push leaves the machine, so no push ships a stale document, and the push that would is refused with the file named.

  • The skill, for Claude Code and Codex since 0.2.0MoreLess

    Claude Code or Codex learns the rules from a skill that ships with each release.

    What it does, in full One skill, written where Claude Code and Codex read it, teaches an agent the rules and starts a corpus with the owner: scan first and show what it found, find where each fact is decided before choosing a repository, one fact end to end, what to hold by hand, and how to report back to the engine's makers.

    Answers #17, #18, #19, #21 asked for by @zakholdsworth · since 0.15.0

    What was planned Scan before you ask, and begin the interview from what the scan found. Find where each fact is decided before choosing the repository: the one the agent was opened in may only be a reader. Say what the scan cannot see and read each finding where it was found. Say what to do when a fact lives in an app's source code: read the owner at run time, else keep it once in the language's own terms, generate source last.

  • Docs from each release since 0.19.0MoreLess

    Every release ships its own docs - start, commands, configuration, checks and proofs, reporting - held to the code by the engine's tests, and this site shows the docs of the release it pins.

    What it does, in full Five pages ship inside each release: the start guide, every command with a worked example, every section of wherefore.json, what each check holds and how to prove one, and how to report back. The engine's tests hold them to the code: every command has its section, every section of the configuration the engine reads is documented, every command a page names exists, and every example is run again on the example company and must print what the page says. The company's site renders the docs of the release it pins.

  • Tell us since 0.12.0MoreLess

    Stuck, or missing something? Tell your agent to tell us: one command writes the report, with the release, the shape of your repository and your words, nothing private, and opens it with the people who make Wherefore.

    wherefore report

    What it does, in full One command writes a bug, a question or a request for the engine's makers - a title, the words, the release, the corpus's shape in counts, the output given, and nothing private - shows it first, and opens it as an issue or prints a link for the person to send. Issues are the inbox: what becomes a feature is the maintainers' call, the roadmap names who asked, and the release writes back what shipped and closes the issue.

    Answers #15 asked for by @zakholdsworth · since 0.14.0

    What was planned Drop the kinds: whether a thing is a bug or a missing feature is the maintainers' judgment, made in triage. Take --title and put the words in the body, so several points stay several points. Add --link, which prints the issue for the person to send and never sends. Never quote the engine's error, which names a path. One report per topic; the agent may draft the words and the person approves them.

  • Releases that reach every client since 0.8.0MoreLess

    When a release ships, this site's own workflow sees it on PyPI, moves the pin, rebuilds, and opens a draft pull request whose checks say what the site still has to describe. No token from the engine, no list of clients: every repository that pins the engine watches for it itself.

    What it does, in full Every repository that pins the engine carries a workflow wherefore init wrote, its own from then on: every few hours, and whenever a person runs it, it asks PyPI for the newest release, and when that is newer than the pin it moves the pin, rebuilds what the release lets through, and opens a draft pull request whose checks say what the corpus still has to describe. A feature the release ships with no words there stops the build, and the pull request quotes it. Nothing merges by itself, no token comes from the engine's makers, and no list of clients exists anywhere: a client needs nobody's permission to be one.

  • Scan any number of repositories at once since 0.13.0MoreLess

    Point the scan at your site, your app, your backend and your docs together: it says what they state in common and where any two disagree, before anything is installed.

    What it does, in full Point the scan at as many places as the company has - the site, the app, the backend, the docs, the deck - in one command. Every place is tagged with where it came from, and the scan says what they state in common and which of those they disagree on, place by place - drift between teams, which no one repository's checks can see, with nothing installed.

  • The scan says what it read since 0.16.0MoreLess

    Beside the result, what each place contributed and what it left unread; an app's own words, read out of its source; a table set apart from the stale copies; and the colours your site states, with the greys that were meant to be one grey, before any brand is declared.

    What it does, in full Beside the result, what each place contributed - how many files of each kind, and the kinds it saw and did not read - so a quiet result is read for what it read. An app's own words are read out of its source. A table, two values said in the same files alike, is set apart from the stale copies. And the colours a site states are counted, with the ones within a shade of each other, before any brand is declared.

    Answers #19, #20 asked for by @zakholdsworth · since 0.16.0

    What was planned Under the first line, for each place, how many files of each kind were read and the kinds seen and not read, so "0 things in common" is never mistaken for agreement. Read string literals out of source code, so an app's own words count. Report two values said in the same files alike as a table, not a disagreement. Count the colours a site states and group the ones within a shade of each other, before any brand is declared.

  • Drift, on the map since 0.20.0MoreLess

    Of the files you write by hand, which state a value in two or more of them that no source holds? The check names each such copy with its files and counts them, the map draws them beside the files, and you declare how many you still allow - a number that only ever falls.

    wherefore check drift

    What it does, in full Of the files a person writes by hand, which state a value in two or more of them that no source holds? A generated file restates its sources by construction; a hand-written file that states a value also stated in another, with no source behind either, is a copy nobody is keeping current. The check names each such value with the files that say it and counts them; the map draws them beside those files with the count in its legend. A drift section declares how many the corpus still allows, the check fails when more drift than that, and when fewer do it asks for the number to come down, so the allowance only ever falls.

  • Launches that wait since 0.21.0 New in 0.21.0MoreLess

    Everything you say is ready has a stage, as a fact: a feature in beta, a site launched. Each stage names what it needs, a stage moves only when those are there, and nothing public names a feature still being built.

    wherefore check launch

    What it does, in full Release is not launch: code ships any day, and what waits is the moment a thing is said to be ready. Every thing with a stage - a feature in beta, a site launched, a roadmap item shipped - has it as a fact in a source; the stages are named once, in order, and each names what must be true from then on: a help doc, a line in the changelog, the name on the feature page. What must not be said before a stage is declared too, so nothing public names a feature still being built. A pull request that moves a thing to a stage it does not have everything for is red, and the check says what is missing in the corpus's own words; for every other thing it says what the next stage still waits on. One ladder is the default; things that move differently - features through building, beta and live, the site through draft and launched - each get a ladder of their own, by name.
